# Automatic and selected sharing

Project category settings control automatic synchronization on each Mac. `true` means Share automatically; `false` means Only when asked. Existing boolean values remain valid. New create/join flows default to automatic memories, skills, and plans, with sessions and ENVs off. Existing project settings, legacy projects without saved settings, and disconnected project catalogs preserve their previous behavior.

Share an eligible local item once from its menu in Orka: choose **Share with team…**, review the frozen snapshot, then confirm sharing. The installed plugin also provides an explicit one-off workflow for local memories and instruction files, full skills, native sessions, and plans, including embedded plans. Both routes preserve the automatic sharing settings and require the connected folder, access, and service capabilities for that item. The private discovery catalog is separate from shared resources and review drafts. Discovery uses the existing source scoping, filesystem guards, complete session/lineage reader, and secret-file exclusions; it does not queue uploads or enable a category.

The plugin has one stdio bridge to the running Orka desktop. Orka owns login, connector consent and all tool execution; the helper never opens an account database or reads credentials. Approve the actual account, service and access in Orka. Every tool derives identity from that approval, without caller-supplied account or proof fields. Shared operations use the desktop-authenticated API. `get_connection_status` explains sign-in/approval/reconnect requirements. Account/service changes, sign-out and revocation permanently invalidate old sessions, including when switching back. A current native session ID is preferred for discovery; ambiguous titles or recency require an explicit selection. See the [plugin guide](../plugins/orka/README.md).

Local `get_connection_status` can explain the Mac's account and connection state without a proof or project content. Sign-out and account/service changes invalidate previous links, including after returning to the previous account. Reconnect through the assistant, approve the native account again, and fetch a fresh remote profile; never switch accounts or retarget a grant automatically. Remote-only clients continue to work. Local reads require `orka.read`; selected publication, installation, retry, and repair require both `orka.read` and `orka.write`.

A preview stores exact cached blob references with a ten-minute token, account, service, project, source, and connected-folder identity. Publication consumes that snapshot rather than rereading a growing conversation. Its durable request ID depends on the resource and base revision. The queue authorizes only that exact payload, survives offline retries, and never grants automatic permission for later snapshots. Category changes do not turn a selected request into a broad grant.

**Send for approval** binds the review destination to the frozen change. An app upgrade or a later grant of publish permission keeps that destination. Older desktops sometimes omitted the choice. Orka routes those queued shares to review when the project is governed or its governance is unknown. A project recorded as ungoverned keeps its direct submission route.

If a refused copy is corrected and the service confirms the new publication, approval request, or conflict, Sync clears the older refusal for that item. Shares still in progress, held for project restore, or belonging to other items keep their place. If **Review changes** cannot refresh a conflict, the dialog stays open and the same button retries the lookup.

Before sending any selected blobs, the native client checks the service's `selectedSharing: 1` capability and registers its existing device identity. `POST /v2/sharing/selected` accepts the existing v2 change schema. It uses ordinary publish authorization and conflict detection, or the existing immutable review-request path when suggestion is permitted. Membership, category/resource access, source audiences, provenance, and session ownership remain enforced by the shared core. Approval-required and conflicted results are not publication success.

Selected sharing uses the existing v2 change wire schema and encrypted ENV format, without deployment variable changes. The native cache adds an isolated local catalog table. The backend endpoint and capability are shared by OSS and managed composition roots; existing servers keep their prior behavior and must be updated before selected publication can complete. This change does not deploy the service or replace installed desktop binaries.

## Verification and rollout

`npm run test:plugin-native` runs separate native broker and thin stdio bridge processes with a synthetic service, in-memory test Keychain and isolated agent homes. It covers native consent and scope failures, lifecycle invalidation, stale sessions, same-account app restart, exact queued retries and complete skill installation. Backend tests retain sharing categories, both hosting modes, membership removal, review policy, conflicts, forbidden ENV files and retry identity. UI checks cover consent, revocation, Settings, compact layouts, keyboard and accessibility. These fixtures do not establish signed installed-app distribution.

Codex accepts the desktop archive and loads both MCP servers; Claude Code validates it and inventories the workflow skills and two servers. These host checks do not claim a production publication. Packaging accepts an explicit executable path for a development build and defaults to the installed app path.

Roll out the shared backend and retire the Dashboard plugin consent routes, then distribute the updated desktop and plugin. The API must advertise `desktopConnector: 1` and implement desktop-authenticated `/v2/connector/tools`. Old remote MCP/OAuth routes return HTTP410; remove the old HTTP connector and reconnect the desktop-only package. Ordinary Dashboard login is unchanged. Selected publication also requires its existing selected-sharing capability. Signed installers, plugin publication and production deployment are separate release steps.
