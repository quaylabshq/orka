# Desktop updates and recovery

## Install Orka

Quit Orka and drag **Orka** from the notarized DMG into Applications. Use the Applications folder in your home directory if your Mac restricts writes to the system Applications folder. Existing users install this first release over their previous Orka app. The app provisions its signed background updater on launch. Workspace and account data stay in Application Support and Keychain.

When a verified release is available, its version appears in the sidebar across workspace tabs. In the collapsed sidebar, open the update icon to see it. Choose **Update and Restart**, open **View changelog** for the GitHub release, or close the card. Orka shows download percentage and a progress bar, then verification and restart status. Idle local plugin connections exit for maintenance; an active plugin request finishes before releasing the runtime lock. If the desktop crashes before opening or repeatedly crashes after launch, the background updater presents Orka’s native repair prompt. It offers an approved forward update or an eligible previous version already on the Mac. An offline restore uses the latest withdrawal policy the Mac has seen.

## Check for updates

Choose **Orka → Check for Updates…** in the macOS app menu, or open **Settings → Updates** under **This Mac** and choose **Check for Updates**. The menu opens Updates and starts a check immediately, including before sign-in in a separate Updates dialog. Existing Settings edits still use the Save, Discard, and Stay prompt before navigation. Checking does not install an update or restart Orka.

Updates shows the installed version, the result of the check, and the last successful check time. **Release notes** starts collapsed; expand it to read the verified release summary, or follow the changelog link to the full GitHub release. Notes remain available for the installed version when it is the release offered by the signed update feed. If a newer release is available, **Update and Restart** uses the same installer and progress as the sidebar. Check failures explain the problem and allow another check; a failed check does not report that Orka is up to date. Development builds without the packaged updater explain that updates are unavailable.

Orka checks at launch, after a change of account, and every four hours while it remains running. A manual check requests fresh update information immediately. A Mac that is offline or asleep checks when the app next runs online.

Early access requires an eligible signed-in Orka Cloud account. Orka labels the offer **Early access update** and checks eligibility again during installation. Public updates are available to signed-out and self-hosted users too. The signed public feed provides withdrawal and recovery policy for all installations.

## Build and promote a release

The [macOS build workflow](../.github/workflows/release.yml) produces a notarized DMG with one app and `Orka-update.zip` with the same stapled `Orka.app`. The updater is signed inside the bundle. The launcher provisions an independently signed copy under Application Support so it can keep running while Orka’s bundle is replaced. A newer embedded updater replaces an older installed helper after signature and trust configuration checks. Changes to the updater protocol, public key, or feed location require a compatible bootstrap release.

1. Keep the Ed25519 private signing key in the protected `macos-update-publishing` GitHub environment as `ORKA_UPDATE_SIGNING_KEY`. Restrict deployment in that environment to `main` and keep its `APPLE_TEAM_ID` variable. Set the same base64-encoded raw 32-byte public key as `ORKA_UPDATE_PUBLIC_KEY` in both GitHub signing environments and as `ORKA_DESKTOP_UPDATE_PUBLIC_KEY` on the managed API. Deploy the API and Dashboard with their authenticated bridge. To enable automatic publication, set `ORKA_DESKTOP_UPDATE_ACTIONS_TOKEN` on the managed API to a GitHub token scoped to `quaylabshq/orka` with repository Actions write permission. The staging workflow authenticates to the API through GitHub Actions OIDC.
2. Build the next version as **universal** and **notarized** from `main`. Verify the DMG and app with its nested updater. Publish the immutable artifacts and include the relevant [unreleased notes](release-notes.md) on the matching GitHub desktop release. The GitHub downloads are public at this step. Dashboard approval controls the offer inside Orka.
3. Publishing the `vX.Y.Z` GitHub release with `Orka-update.zip` queues **Publish macOS update policy** with **stage** on `main`. The protected job verifies the notarized archive and Apple team, saves `Orka-update-manifest.json` to the run, and submits the signed manifest to **Releases** as a draft. Finalize the GitHub release notes before publishing. The workflow includes up to 4,000 UTF-8 bytes of those notes in the signed draft. For a release published earlier or by an Actions job using `GITHUB_TOKEN`, dispatch **stage** on `main` with the version and optional notes. If submission fails, re-run the stage job when the managed API is available or import the saved manifest from **Releases**.
4. Add testers by their verified Orka Cloud email addresses and choose **Enable early access**. Test from an installed rollout-capable build. Choose **Pause early access** to stop offers while investigating a problem. When ready, explicitly approve public release in the Dashboard. The initial release admin is the verified `saket@quaylabs.dev` account. Each change is recorded in the Dashboard.
5. Dashboard approval queues **promote** on `main` when managed publication is configured. The protected job verifies that the downloaded notarized archive and metadata match the managed API's signed public approval. The Dashboard tracks publication and shows the release as live after the API confirms the matching version and archive digest in the signed public feed. Open the linked workflow run to diagnose failures and retry from **Releases**. When automatic publication is unavailable, run **Publish macOS update policy** on `main` with **promote** and the approved version. The default public feed is `https://raw.githubusercontent.com/whysosaket/orka/desktop-updates/macos.json`. An overridden `ORKA_UPDATE_FEED_URL` must serve the same signed policy.
6. Keep automatic renewal of the 48-hour signed policy running. Monitor failed renewals and alert before expiration. Renewals and withdrawals use the signed policy independently of the rollout API.

Rollout-capable desktops can discover the approved release with a fresh signed policy after approval. Clients that read only the public feed discover updates after protected promotion, including the first build they install with account-based eligibility. The managed API provides a read-only check at `GET /v2/desktop-updates`. Pass `installedVersion` to compare with the current Mac version.

```sh
curl --fail --silent --show-error 'https://api.tryorka.ai/v2/desktop-updates?installedVersion=0.3.15'
```

The response includes the approved version and signed candidate for the current audience, or a null manifest. Eligibility, architecture, data epoch and the latest signed withdrawal policy all affect which candidate a Mac can install.

## Withdraw a bad release

Pause an early-access candidate from the Dashboard to stop serving new offers. If a version must be blocked for install, startup or recovery, run **Publish macOS update policy** with **withdraw** and the affected version. The withdrawal is permanent for that version. Optionally raise `minimum_version` when old builds must be excluded from installation and restore. The updater rechecks a fresh signed policy before an approved download can replace Orka. A Mac that has already observed a withdrawal remembers it across offline sessions. A Mac needs a successful feed refresh to learn about a new withdrawal.

Build the fix with a higher version and repeat staging, approval, and promotion. The updater can fetch it independently of the UI and sync process. Keep the old GitHub release for audit and mark it withdrawn in its release notes. Clients select from the signed desktop policy, including when the newest GitHub release is a server release.

## Data compatibility and acceptance

Increment [the desktop data epoch](../apps/mac/recovery/data-epoch) for a change that prevents the previous build from safely opening local data, retaining pending sync work, or using the supported server contract. The updater can install a forward version with a higher epoch and offers a local restore only within the same epoch. Test the old and new client against the same data and supported server versions before keeping the epoch unchanged.

Orka 0.3.12 uses data epoch 2. Earlier desktops do not preserve the frozen selection of a pending session copy during permission or source removal, so recovery must not restore them over the new pending work. The forward update preserves existing local data; restoring a pre-0.3.12 desktop over that data is unsupported.

Orka 0.3.14 uses data epoch 3. It freezes the selected session version for a queued conflict resolution and preserves that private snapshot when access or a source folder is removed. Desktop 0.3.13 does not understand that pending selection and can discard it during cleanup. Forward updates retain existing local data; restoring 0.3.13 or earlier over epoch 3 data is unsupported.

Orka 0.3.19 uses data epoch 4. For a connected subfolder or worktree, Orka can bind Claude memory to the repository's native memory directory. Older versions expect a different directory and can interpret an absent memory file as a deletion. Forward updates keep existing bindings. The recovery helper requires another epoch 4 build for a local restore.

The session storage update uses data epoch 5. The desktop reads private session metadata from the existing catalog and uses the native transcript as the source for new catalog rows. Epoch 4 builds expect stored transcript bytes for those rows. Forward upgrades preserve existing catalog snapshots and pending work. The updater requires an epoch 5 build when offering a local restore. To use an older app again, restore a complete epoch 4 app-data backup taken before upgrading.

### Reclaiming old session snapshots

After upgrading, refresh the session catalog for projects you still use so their private sessions can use the originals. The cleanup command reports estimates for one profile at a time. It defaults to a read-only inspection. Use `--profile NAME` to select another profile.

```sh
"/Applications/Orka.app/Contents/MacOS/orka-desktop" --orka-clean-session-blobs
"/Applications/Orka.app/Contents/MacOS/orka-desktop" --orka-clean-session-blobs --apply
```

For apply, quit Orka and stop background sync and CLI jobs using that profile. Close any older copies of the app before maintenance. Current app processes hold a profile storage lock for their lifetime, including plugin and export operations. If a process holds the lock, apply reports the profile as in use. Rerun the dry run after quitting if a database journal prevented a consistent read.

The report shows eligible and removed file counts and allocated bytes by store, along with counts by skip reason. It protects referenced resource, pending, draft, conflict, preview, and older catalog snapshots across the profile's account databases. A missing, unreadable, or unsupported database blocks cleanup for that profile. Legacy accounts can omit the drafts table and retain an empty usage outbox. Cleanup is limited to verified unreferenced Codex and Claude transcript files in Orka's stores. Native originals and exported archives are outside those stores. Rerun after an interrupted apply to finish the scan.


LaunchServices starts the native desktop executable directly, preserving its process identity for the macOS menu bar. Before opening the workspace, the desktop holds the installation locks and asks the bundled recovery launcher to check cached withdrawal and crash state and start the health watcher. The legacy launcher entry point remains available for installed hooks and background commands; GUI launches through it return to LaunchServices rather than replacing a running process. The background updater records startup and exit health locally. For a regular update, it verifies the calling desktop process and rechecks the approved version and archive digest. The installer stages a signed full bundle on the installation volume, waits for foreground and background processes to release their shared runtime lock, and swaps the bundles atomically. An interruption leaves either the previous or the new complete bundle at the same path. The updater and application data live outside that swap.
